## What Post-its is

Post-its is a web app for post-it notes on an infinite canvas. Where you
put a note is how you prioritise and group it. The original
differentiator is co-presence. You see who else is on a board, and you
can hop to someone's board to leave them a note. This week the project
added a second differentiator, agent accessibility (described below).

The stack is a React client (Vite), a Node server using `ws`, and SQLite
via `node:sqlite`, all on one 256MB Fly.io machine. `spec/*.test.ts`
(vitest) tests the HTTP and WebSocket API only. The only browser-level
testing is the project's own `verify-postits` skill (described below).

`README.md` defines what good means: the app is fully functional, easy to
use, and gets good feedback from real people. Judge every new feature idea
against that, not against scope or cleverness.

## The pivot decided this week (22 Oct)

The full rationale is in the "Current spine" section at the top of
`fixed-idea.md` and in the message of commit `7cb52a7`. In short, the
project had two candidate directions.

1. A minimal post-it board, the original thesis in `README.md`.
2. 3D homes and halls, portals, a job board, a coin economy, levels, dust,
   and day/night. `more-ideas.md` has the full brainstorm, and the
   superseded "In one paragraph" section of `fixed-idea.md` records it as
   decisions.

Direction 2 is parked, not cancelled. It doesn't share a thesis with
direction 1, because it is gamified virtual coworking rather than
note-board HCI. It was also consuming budget and scope without a clear
product reason. Nobody deleted the parked sections of `more-ideas.md` or
`fixed-idea.md`. Each file has a note at the top that points to this
decision.

The new build order is checkpoints E to H in `docs/backlog.md`.

- E, note status. Notes move through `todo`, `doing`, and `done`, with
  `approved` reserved for a future job board. Shipped, see "Current state"
  below.
- F, a read-only MCP triage server. A user's own agent (Claude Desktop,
  Claude Code, and similar, not a hosted chatbot) can list, summarise, and
  flag notes on their board through MCP tools. The project pays no
  inference cost. The user creates an API token in the app and pastes it
  into their agent's config. Fully designed but not built, see the ADR
  below.
- G, agent discoverability. This covers robots.txt, a sitemap, semantic
  HTML, pages served as markdown on request, and documentation for
  `/api/*`. Two external scanners the user cares about motivate part of
  it, `isitagentready.com` and `is-agentic.com`. Both run concrete
  technical checks. They look for an MCP server or manifest, OAuth
  discovery metadata, AI rules in robots.txt, markdown content
  negotiation, semantic HTML and heading structure, rate-limit headers,
  and self-serve onboarding. The previous session's transcript has more
  detail. Not designed or built.
- H, offline-first for a single player. A service worker and local state
  in IndexedDB, synced on reconnect. It deliberately does not handle
  multi-user offline merges or CRDTs. Only one writer exists while
  offline, so it needs no conflict resolution. Not designed or built.

Later the user raised a job-hunter or guild idea, where someone posts a
job, others claim it, and the poster verifies completion. This is the
parked job board from `more-ideas.md` §4–5 and `fixed-idea.md` §4. When
asked, the user chose to keep it parked. Don't build it without asking
again.

    `revoked_token`.
  - The MVP allows one token per user, but the schema can hold several
    later.

## Tooling already set up

Read this before building your own versions.

- `.cursor/skills/verify-postits/` is a project-local Claude Code skill,
  not a Post-its feature. It drives the running app like a user through
  `claude-in-chrome` and checks the SQLite database directly, so a feature
  is proven to work rather than assumed from a clean compile. Its
  `features/` folder has one file per feature: login, create and edit
  note, move/select/label, live cursors and presence, channels and chat,
  and note status. Use it to verify any new feature, and add a
  `features/<name>.md` file when a feature ships. Login, create note, and
  note status have been run end to end. The other three were written from
  reading the code and haven't been run yet, and their files say so.
- `~/.claude/rules/pstack-models.md` sets the model and effort for each
  pstack role. The baseline is medium/high, with judgment and synthesis
  roles at xhigh. The user wanted it easy to lower if the $200/week course
  budget gets tight. To lower it, re-run `/pstack:setup-pstack` or edit
  the effort values by hand.
- The worktree workflow is described in `CLAUDE.md` at the repo root. Read
  it there rather than relying on a copy here. In short, each feature gets
  a worktree at `.claude/worktrees/<name>` on branch `feat/<name>`. Shared
  and harness changes are committed on `main` in the root checkout, and
  `scripts/sync-worktrees.sh` then merges `main` into each worktree.
  Finished features are merged into `main` from root.
- The user runs parallel agent sessions in Herdr, one workspace per
  feature. Checkpoint E was built that way by hand. That pattern is now a
  pipeline: the `orchestrate-postits` skill and `scripts/orch/` start a
  builder and then a reviewer per feature, each in its own worktree with its
  own ports. The summary is in `docs/orchestration/README.md`. It was tested
  end to end with a throwaway feature, but hasn't built a real one yet.

## Suggested skills for the next session

- `how`, to relearn how an existing subsystem works (such as the note
  schema or the WebSocket protocol) before proposing a feature on top
  of it.
- `why`, when a proposal would change an existing decision, such as
  reviving the parked 3D direction or dropping the read-only limit on the
  MCP v1. It finds the original rationale so you can treat it as a
  constraint instead of guessing.
- `principle-exhaust-the-design-space`, through `/pstack:architect` or on
  its own, for a feature idea with no precedent in the codebase. Sketch
  two or three competing designs before choosing one, as ADR-0001 did.
- `arena`, when a brainstormed feature has a real design fork that is
  easier to compare in code than to debate.
- `/pstack:poteto-mode` in general. The user runs the whole project
  through the poteto-mode playbooks, and checkpoint E used the Feature
  playbook. Invoke it for any new build session instead of building ad
  hoc.
- Don't use `figure-it-out` or `architect` just to run a brainstorm.
  Poteto-mode's own rules say product and preference decisions, such as
  "should jobs pay coins" or "is 3D worth it", belong to the user and get
  settled in conversation. Only forks you can test empirically should go
  to a skill-driven sketch or prototype.
